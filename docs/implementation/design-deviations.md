# Design Decisions and Deviations

This register records decisions that differ from or resolve open/proposed items in [`design.md`](../../design.md). Keep the source design unchanged unless explicitly approved. Update this register as later chapters settle deferred items.

Statuses:

- **Resolved:** an explicit decision exists; implementation must follow it.
- **Deferred:** intentionally postponed to a later chapter.
- **Open:** needs an explicit decision before the owning chapter is implemented.

| ID | Design reference | Original design / open point | Recorded decision | Status / follow-up |
|---|---|---|---|---|
| DD-01 | §2.2, D1 | Factory repository may be standalone or vendored. | This repository is the standalone factory repository. Target projects are selected explicitly with `--project`; their project configuration remains in `.factory/project.json`. | Resolved |
| DD-02 | D7; §2.1 | Default concurrency is one until the dashboard; exact enforcement point is open. | No parallel branch/job execution initially. Chapter 1 serializes writes per job; the runner/scheduler must enforce one active job globally when introduced. | Resolved; enforcement deferred to runner |
| DD-03 | §1.2, §2.1, §2.2, D14 | `branch-per-job` proposed as default; `direct` may reset to `base_sha` on failure. | Start with direct mode. A job begins as metadata only. After spec approval, a person prepares an existing, valid, unoccupied local branch and the factory attaches a worktree. No Git tag, automatic branch creation, reset, force, or branch deletion. Branch-per-job and parallel execution are later work. | Resolved; exact operational contract in Chapter 1 |
| DD-04 | §2.2; Chapter 1 proposal | `job.json` is described as the sole source of truth, with a separate append-only event log. | `events.jsonl` is authoritative; `job.json` is a rebuildable atomic snapshot. A stale snapshot is reconstructed from valid events; a corrupt/incomplete log fails closed. | Resolved |
| DD-05 | §2.1; Chapter 9 | Diagram lists `BUDGET_EXHAUSTED` as a state, while Chapter 9 sends budget exhaustion to `NEEDS_HUMAN`. | `BUDGET_EXHAUSTED` is an event/reason; the job state becomes `NEEDS_HUMAN`. | Resolved |
| DD-06 | Chapter 1 proposed `job.json` fields | Risk, budget, hash, feature, session, and gate/review round fields are listed before their owning workflows exist. | Chapter 1 stores only the versioned job/state/project/branch/worktree core. Add later fields with their owning chapters. | Resolved |
| DD-07 | Chapter 1; D11 | Pydantic and Python 3.12 are proposed; implementation setup is absent. | Python >=3.12, verify with available 3.14; Pydantic is the only planned runtime dependency. | Resolved |
| DD-08 | §2.1; Chapter 1 lifecycle | Original branch setup occurs at job start; the user workflow places branch selection after spec approval. | `job new` creates metadata without branch/worktree. After spec approval, a person prepares the local branch and the factory explicitly attaches it, before TDD tests. | Resolved |
| DD-09 | §2.2; Chapter 3 | Target `.factory/checks.py` is the per-project checks contract; gate implementation lives in the factory. | Factory-side gate/dispatcher invokes the target project's checks contract. Checks execution remains outside Chapter 1. | Resolved |
| DD-10 | Chapters 5–6; Chapter 4 | Chapter 5 proposes interactive spec approval; Chapter 6 proposes a separate test-author and locked tests. | For M1, a person creates and approves the spec and TDD tests; AI may assist. Lock both before building, and do not allow the builder to edit them. A separate AI test-author workflow is not part of M1. | Resolved for M1; approved 2026-11-23 |
| DD-11 | §2.1; Chapter 1 transition proposal | Generic `transition` exists, but its interaction with guarded normal transitions was not fully settled. | Generic CLI transition is limited to escalation/resume; normal forward transitions require their owning commands and precondition checks. `SPEC_APPROVED` is required before branch attachment; Chapter 5's `approve-spec` reaches that state. | Resolved; approval workflow is Chapter 5 |
| DD-12 | Chapter 1 CLI proposal | Output/error shapes and numeric exit-code categories are unspecified. | Success is JSON on stdout; errors go to stderr; exit `2` means usage/configuration error and `1` means operational failure. | Resolved in the Chapter 1 contract |
| DD-13 | Chapter 1 factory config | The config location is known, but factory-root discovery is unspecified. | The CLI runs from the factory repository root; the current working directory is the factory root for `config.json` and relative data paths. | Resolved |
| DD-14 | D14 `.factory/project.json` | The project config proposes a `work_branch` template. | The person prepares the exact local branch after spec approval and passes it to `worktree attach`; no branch template or automatic branch creation is used initially. | Resolved; branch-per-job remains deferred |
| DD-15 | Chapter 1 worktree release | Interrupted release recovery is not specified. | CH1-03 journals a release intent before Git removal; `repair` safely completes removal or finalizes the journal if Git already removed the worktree. A missing path that Git still registers fails closed. | Resolved; approved during CH1-03 implementation |
| DD-16 | Chapter 1 worktree attach recovery | Repair was specified not to fetch, but an interrupted fetch before `WORKTREE_BASE_FETCHED` leaves no journal evidence that a cached remote-tracking ref is fresh. | If attach recovery has no recorded `base_sha`, repair retries the configured base fetch and records its result before attaching. If `base_sha` is already recorded, repair does not fetch again. Never infer fetch success from a cached ref. | Resolved; approved during CH1-03 follow-up |
| DD-17 | Chapter 2, D13 | Headless CLI configuration isolation was open; verified flags might not prevent user MCP configuration from loading. | Accept user MCP configuration loading as a known Chapter 2 security limitation. The runner must still use `--disable-builtin-mcps`, `--no-custom-instructions`, `--no-auto-update`, and explicit tool permissions. Full `COPILOT_HOME` isolation is deferred and must not be implied by these flags. | Resolved; accepted 2026-11-22, follow-up remains deferred |
| DD-18 | Chapter 2 runner interface and preflight | `RunResult` specifies artifact paths, but a failed preflight must not allocate a run directory. | On preflight failure, `run_agent` returns an `ERROR` result with `paths={}` and a diagnostic; no run directory is created. | Resolved; explicitly approved by user |
| DD-19 | Chapter 3; Appendix A | Gate proposes risk recomputation, and Appendix A illustrates numeric file/line diff budgets before Chapter 7 defines risk routing. | Chapter 3 does not recompute risk and does not enforce numeric file/line budgets. It reports risk as deferred; Chapter 7 owns the effective-risk calculation. | Resolved; approved during Chapter 3 review |
| DD-20 | Chapters 2, 8; §2.2 | Design assigns push and draft PR creation to the orchestrator; the user's workflow assigns publication to a human after review. | Builder may commit but may not push or open a PR. A human publishes after review; Chapter 8 must define recording the issue/PR reference and the transition to `PR_OPEN`. | Resolved; approved during Chapter 3 review; state workflow deferred to Chapter 8 |
| DD-21 | Chapter 3; Appendix A | Scope input, checks report schema, and enforcement of protected factory job data are underspecified. | Gate consumes an explicit base SHA and factory-controlled scope manifest; includes tracked and untracked target-worktree changes; validates a strict JSON checks report; target checks run only if unchanged from base. The orchestrator is the sole writer of factory job data. | Resolved; approved in Chapter 3 contract on 2026-11-22 |
| DD-22 | Chapters 2, 3, 4, 8, 9 | The Runner materializes `.factory/task.md` inside the target worktree; task generation, archival, and review-repair input are not fully specified. | Each session gets a new immutable task snapshot derived from the approved spec/feature; review findings add repair instructions without silently changing spec/scope. Preserve snapshots in factory job artifacts. Gate excludes only an untracked `.factory/task.md` runtime input; staged or committed changes to it fail. | Resolved during Chapter 3 review; task generation/retry implementation deferred to Chapters 4/9 |
| DD-23 | Chapters 1, 4–6; M1 | Chapter 4 depends on approved specs and red TDD tests, but Chapter 1 reserves their normal approval/readiness commands for Chapters 5–6. M1 uses manually prepared inputs. | Add a narrow Chapter 4 M1 registration path for human-created, human-approved spec and test artifacts. AI may assist authoring, but registration only records approval/hashes and validates readiness; it does not author the artifacts. The builder cannot modify the locked inputs. The target checks script runs the baseline-red check and binds its report to the manifest hash and `work_branch_start_sha`. | Resolved; approved 2026-11-23; exact schema in Chapter 4 contract |
| DD-24 | Chapters 3–4 | Chapter 3's Gate exposes only whole-project `fast|full` checks, which cannot gate one TDD slice while later slices are intentionally red. | Extend Gate with baseline checks that exclude pending job tests, selected-slice TDD checks, and final full checks. Preserve scope/protection validation; Gate remains state-neutral and the orchestrator records slice status and advances job state. | Resolved; approved 2026-11-23; exact interface in Chapter 3 addendum and Chapter 4 contract |
| DD-25 | Chapters 4–6; test lifecycle | Test ownership, project persistence, and job-local diagnostics are conflated. | Long-lived behavior tests from Test Author or Builder belong in the target project's established test structure and standard test process. Only explicitly temporary diagnostics may remain job-local. G1 approves the independent Test Author set before Builder starts; Builder may add tests but cannot change that set without re-approval, a new hash, and baseline-red validation. | Resolved; approved 2026-11-24; see [test lifecycle and Feature Validation decisions](./test-lifecycle-and-feature-validation.md) |
| DD-26 | Chapters 5–6; Gate report | ACs lack stable IDs and an explicit test mapping; manual AC could be represented as passing without automated evidence. | Give each AC a stable ID and map every gating AC to automated test IDs. Manual execution is not a Gate pass path; move non-automatable checks to a separately approved human-review checkpoint or outside automated gating. Missing, failed, skipped, or unexecuted required checks fail the Gate. | Resolved; approved 2026-11-24; schema details belong to the follow-on contract |
| DD-27 | Chapters 3–4, 7, 9 | Proposed separate Feature Validation Gate, post-Gate commits, immediate retries, and risk-based E2E overlap existing workflow and deferred chapters. | Keep one Gate engine: per-slice Gate plus the existing final full Gate after all slices. Commit before Slice Gate and mark the slice passed only after Gate PASS; preserve failed work. Keep Chapter 4/M1 retry-free; define retries in Chapter 9 and risk-based E2E in Chapter 7. | Resolved; approved 2026-11-24; follow-on implementation contracts required |
| DD-28 | Chapters 3–6 | Test Author tests created after `work_branch_start_sha` can conflict with protected-path checks and the final Gate's original comparison base. | After G1 and baseline-red validation, record a durable test-only checkpoint. Keep the original branch base for the complete job/review diff and use the approved Test Author checkpoint as the implementation Gate base. Validate Test Author changes separately against the original base and restrict them to approved test paths. This is post-run scope enforcement, not an OS sandbox. | Resolved; approved 2026-11-24; checkpoint event and SHA fields required before Test Author implementation |
| DD-29 | Chapter 3; Gate artifacts | Current report v1 omits AC outcomes, the Test Author checkpoint, and a precise tested head. | Retain one Gate CLI/engine and introduce report schema v2 with gate type, job/features/slice, `job_base_sha`, `gate_base_sha`, `head_sha`, timestamps/duration, required check outcomes, AC-to-test results, input hashes, test execution summary, and log references. Risk stays deferred until Chapter 7 implements it. | Resolved; approved 2026-11-24; exact schema belongs to the follow-on Gate contract |
| DD-30 | Target project CI and test setup | Persistent tests need future execution, but automated CI edits or a universal test structure are unsafe. | Detect existing project test/CI conventions. Do not modify CI or add test infrastructure without explicit human approval; propose missing infrastructure as a separate project scope. | Resolved; approved 2026-11-24 |
| DD-31 | Factory quality evaluation | Unit tests alone cannot establish end-to-end agent quality; real-agent tests are expensive and less reproducible. | Test the Factory with unit, CLI/contract, temporary-Git integration, and security/invariant suites. Use a small representative set of real-agent golden tasks for end-to-end quality and cost evaluation, not as the only or routine fast-CI defense. | Resolved; approved 2026-11-24; details in [test lifecycle and Feature Validation decisions](./test-lifecycle-and-feature-validation.md) |

## Review workflow

1. Record each approved decision with a concise identifier and source section.
2. Mark unapproved proposals as **Open**, not as requirements.
3. When a later chapter resolves a deferred item, add the resolving chapter/contract and update the status; do not rewrite the original design silently.
